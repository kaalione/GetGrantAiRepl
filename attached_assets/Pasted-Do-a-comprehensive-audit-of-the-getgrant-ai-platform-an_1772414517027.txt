## PART 3 — CRITICAL PATH ANALYSIS

The single most important user outcome is:
"User finds a relevant grant AND submits a complete application"

Analyze the current funnel for this outcome:

STEP A: Discovery — Can users find grants relevant to their business?
  - What is the matching algorithm's input? (what company fields does it use?)
  - What is the typical score range for a matched grant? (top 10 grants)
  - Are the top 10 matches actually relevant for a typical Swedish SME?

STEP B: Evaluation — Can users quickly decide if a grant is worth applying for?
  - How much information is on the grant card in /bidrag?
  - What's on the grant detail page?
  - How fast/slow is the AI analysis? Is it always triggered or optional?

STEP C: Application — Can users complete an application without leaving the platform?
  - What grant sources have custom templates vs generic template?
  - What information does the wizard ask for?
  - How long does generation take?
  - What's the quality of generated content? (word count, sections)

STEP D: Submission tracking — Can users track what they've applied for?
  - Is there an applications list page?
  - Can users mark grants as "submitted" or "funded"?
  - Is there a success fee flow when a grant is funded?

## PART 4 — FRICTION POINTS & OPTIMIZATION OPPORTUNITIES

For each step in the critical path, identify:
1. The biggest friction point (what makes users drop off?)
2. The quickest fix to reduce that friction
3. Whether the fix is a frontend change, backend change, or content change

Also check:
- Is the onboarding wizard asking for all the fields needed for good matching?
  Missing fields = worse matches = user frustration
- Are there grants in the database with empty/missing titles or descriptions?
  Run: SELECT COUNT(*) FROM grants WHERE title IS NULL OR description IS NULL OR LENGTH(description) < 50;
- What % of grants have structured_eligibility extracted?
  Run: SELECT 
    COUNT(*) as total,
    COUNT(CASE WHEN structured_eligibility IS NOT NULL AND (structured_eligibility->>'confidence_score')::float >= 0.3 THEN 1 END) as good,
    ROUND(COUNT(CASE WHEN structured_eligibility IS NOT NULL AND (structured_eligibility->>'confidence_score')::float >= 0.3 THEN 1 END) * 100.0 / COUNT(*), 1) as coverage_pct
  FROM grants WHERE status IN ('open','upcoming');
- Are there any JavaScript errors in the browser console that would block users?
  Check server logs for any 500 errors in the last 24h.
